# Ресторан — объединённый проект

**Основой служит первый архив.** Во втором не обнаружено ни одного уникального файла: в первом есть все его файлы и дополнительно расширенный складской и продуктовый функционал. Поэтому устаревшие варианты из второго не перезаписывают новые компоненты первого.

## Быстрый запуск (Windows, PowerShell)

Требуется **Node.js 22+** и npm. Запускать команды из папки `restaurant-app` (в ней лежит `package.json`).

```powershell
npm ci
npm run dev
```

Открыть **http://localhost:5173**. Команда запускает **и React-приложение, и локальный demo API**. Настоящий C#-сервер для этого сценария не нужен. Демо-пользователь: `owner@demo.test`, пароль `Demo123!`. Коды подтверждения новых аккаунтов показываются на странице подтверждения в demo-режиме.

Важное: `npm run dev` использует **mock-режим**, даже когда в сети нет настоящего бэкенда. Он хранит тестовое состояние локально, не является production-бэкендом и не рассылает настоящие письма.

**Если демо-логин пишет про `accessToken`:** демо-логин не требует токена заранее, он выдаёт его сам. На странице входа будет синий блок **«Демонстрационный режим»** и кнопка **«Войти как владелец (демо)»**. Если вместо этого виден жёлтый блок **«Подключён настоящий бэкенд»**, закрыть приложение (`Ctrl+C`) и запускать именно `npm run dev`, **не** `npm run dev:live` и не отдельно `vite`. Команда `npm run dev:demo` делает то же самое. При необходимости откройте новое окно браузера или сделайте `Ctrl+Shift+R`.

Проверка API без токена: `http://localhost:5173/demo-api/health` должен возвращать `{"mode":"demo","ok":true}`. Если 502, демо-сервер не запущен. Для сброса демо-состояния (сбросит все изменения в нём) остановите сервер и выполните `npm run demo:reset`.

Если **в live-режиме** сервер требует `accessToken` на `POST /api/Authority/AuthorizeUser`, это проблема защиты публичного маршрута на **реальном бэкенде**. Нужен анонимный доступ к login (например, атрибут `[AllowAnonymous]` в ASP.NET Core), без ослабления защиты остальных маршрутов. Демо-аккаунта на реальном сервере нет, если вы его сами не создали.


## Подключение существующего C#-бэкенда

1. Запустите **свой** бэкенд отдельно; в его коде ничего менять из этого архива не требуется для запуска фронта.
2. Откройте `.env.live` и задайте в `API_PROXY_TARGET` настоящий адрес бэкенда. Значение `http://localhost:5067` — **только пример**, меняйте порт на свой.
3. Запустите:

```powershell
npm ci
npm run dev:live
```

4. Откройте **http://localhost:5173**. Запросы `/api/*` и `/ws/*` идут через Vite-прокси на `API_PROXY_TARGET`, поэтому CORS в локальном браузере не требуется. Для HTTPS/WSS или для сервера с другим WebSocket-маршрутом может понадобиться указать `VITE_REALTIME_URL` отдельно. Если нужны прямые запросы к бэкенду (без Vite-прокси), уберите `API_PROXY_TARGET`, добавьте `VITE_API_URL` и настройте CORS на бэкенде.

**Важно:** реальная интеграция зависит от того, какие маршруты и JSON-схемы действительно реализованы вашим C#-сервером. В архивах его исходников нет. Прокси решает вопрос соединения и CORS, но **не реализует отсутствующие API-методы**. Маршруты фронтенда перечислены ниже.

## API фронтенда

Авторизация:

- `POST /api/Authority/RegisterUser`
- `POST /api/Authority/VerifyUser`
- `POST /api/Authority/AuthorizeUser`
- `POST /api/Authority/ResendCode`

Рестораны и учёт:

- `GET /api/Restaurant/my`
- `POST /api/Restaurant/create`
- `POST /api/Restaurant/CreatePOS`
- `GET/DELETE /api/Restaurant/:id` (см. вызовы в коде)
- `GET /api/Restaurant/:id/snapshot`
- `GET/PUT /api/Restaurant/:id/products`
- `GET/PUT /api/Restaurant/:id/menu`
- `GET /api/Restaurant/:id/employees`
- приглашения и POS: `/api/Restaurant/:id/invitations`, `/api/Restaurant/:id/pos`, `/api/Invitation/accept`
- подтверждения поставок: `POST /api/Supply/:id/accept` или `/reject`
- списание просрочки: `POST /api/Restaurant/:id/expiry/:batchId/approve`
- поток обновлений: `WS /ws/restaurants?restaurantId=...&access_token=...`

Конкретные методы HTTP в модулях `src/shared/api/*.ts`; источником истины для маршрутов служит `src/shared/api/config.ts`. Если бэкенд работает по другим адресам, потребуется адаптировать эти вызовы **под реальный контракт**, а не угадывать JSON.

## Что есть в проекте

Вход, регистрация, проверка email; рестораны и роли; аналитический дашборд; склад **по партиям** и **по продуктам**; каталог с единицами измерения и сроком хранения до секунды; меню и рецепты; поставки; сотрудники; POS; просрочка; WebSocket-подписка. Макет и структура приложения сохранены из первого архива.

## Проверки

```powershell
npm run test           # встроенный demo API
npm run test:client    # клиентская логика; после npm ci
npm run check          # линтер, API/клиентские тесты и сборка
```

Дополнительно `npm run test:ui` требует отдельно установленного Playwright с Chromium, как указано в `tests/ui.smoke.mjs`.

Если порт 5173 занят, закройте другое приложение на нём. Если реальный сервер недоступен, проверьте `API_PROXY_TARGET` и запущен ли ваш бэкенд. Если вместо данных сервер отдаёт 404 — API-метод отсутствует или его путь отличается. Если не работает live-поток, временно выставьте `VITE_ENABLE_REALTIME=false`: обычные HTTP-запросы продолжат работать.
